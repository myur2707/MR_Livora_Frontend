# Step 11: dashboards and reports

Platform Dashboard displays society lifecycle counts, total societies and pending verification from the limited platform endpoint. It never requests tenant financial/private aggregation. `/society/dashboard` selects the committee dashboard for the explicit dashboard-management permission; residents retain their existing dashboard. Committee cards show active/occupied flats, current people/occupancy types, pending complaints and published notices. Financial cards require finance.read and show current outstanding plus month-to-date recorded collections/cash after returns.

`/society/reports/{outstanding,collection,cash-collection,payments,residents,flat-occupancy,billing}` is a lazy-loaded report area. Finance permission exposes financial reports; directory-management permission exposes resident/occupancy reports. Guards are usability controls: the backend validates every session, permission, filter and record reference. Accountant has no resident-directory access; Committee Member has no implicit financial reports. Platform role alone grants no tenant reports.

Date/search/status/sort controls, optional building/flat/period/collector pickers, payment method and occupancy type send validated filters to the server. Pages contain 20 rows; summary cards always describe all matching rows. Date errors are associated with fields. Text/cells use interpolation, never unsafe HTML. Table regions are keyboard focusable and scroll on narrow screens; shared theme/focus tokens remain in use.

Current balances are not historical balances: billing dates select billing-period starts; payments select original payment dates and include all later returns; collections select each event's business date; resident creation uses society-local day boundaries; occupancy ranges select interval overlap. Ranges require both dates or neither and allow at most 366 days. The report displays its society time zone and balance date. Legacy reversals without a business date are explicitly marked LEGACY_UTC.

CSV requires the backend's separate export permission. Downloads include all matching rows up to 5000, not only the current page. Server-safe quoted/formula-neutralized CSV is preserved as text and downloaded through a temporary in-memory Blob; its URL is revoked immediately. Oversized-export feedback asks for narrower filters. In-flight downloads are discarded if identity, society, route or authorization changes. Reports remain memory-only; no local/session storage is used. The worker's static route allowlist includes report shells only, with no data groups or private API/CSV caching.

The backend's additive `db:report-permissions` command/managed local upgrade provisions the new capabilities. No schema migration or package upgrade is added by Step 11. Existing notice/complaint, billing/payment and resident privacy behavior remains intact.

Run `npm run check` and `npm run test:e2e`. New browser coverage checks full-filter totals across pagination, associated date errors, CSV contents/limits, late-context downloads, role-specific guards/dashboards, 320px accessibility in both themes and expired-session clearing. Real MySQL authorization/reconciliation tests live in the backend repository. Physical PWA installation and device-specific downloads remain browser/OS checks.
