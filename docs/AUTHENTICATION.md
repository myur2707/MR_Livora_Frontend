# Step 3 frontend authentication

The Angular application uses server-managed HttpOnly cookies through relative same-origin `/api/v1` requests. HttpClient's functional interceptor adds credentials, no-store and a memory-only X-CSRF-Token only to these requests. It does not forward tokens to absolute third-party URLs. Identity, current society and permissions are held in Angular signals only; neither localStorage nor sessionStorage contains auth secrets. Theme preference remains the only persisted frontend setting.

Login, forgot-password and reset-password are real accessible forms with the existing shared field feedback. Server errors are mapped from reviewed codes; arbitrary server text never enters the UI. Passwords are cleared after failure/success. Reset links use `/reset-password#token=...`; the fragment is removed from the address/history immediately and retained only in the reset component until used. Reloading after removal requires reopening the mail link. Password reset does not sign in automatically.

The protected workspace selector displays current memberships from the server, posts a candidate society ID to the backend, refreshes current context and navigates to the society shell. Platform and society routes re-read the session on navigation. Platform access never implies society access. Revoked/expired or unavailable sessions fail closed. Guards and filtered navigation are UX only; backend authorization remains required on every request. No financial/private business screen was added.

For local development run the backend on 127.0.0.1:3000 and `npm run dev` here on 127.0.0.1:4200. The public proxy configuration forwards `/api/**`; backend APP_ORIGIN must match the browser origin exactly. Production must route both Angular and API under the same HTTPS origin; the static preview server is not an API server. Frontend configuration contains no secrets. See the backend's docs/security/AUTHENTICATION.md for database provisioning, password hashing, SMTP, development seeding and production cookies.

The PWA keeps the existing static-only policy with exact /workspace and /reset-password shell navigation entries. No API data groups/runtime patterns, no private data caching, no offline authenticated access. A cached shell contains no session or user data; a fresh network session is required before entering a protected route. Offline users can open the sign-in shell and retry once connected.

Checks: `npm run check` and `npm run test:e2e`. Unit tests cover CSRF/credential forwarding boundaries, expired/offline identity, least-privilege guards, safe errors and open-redirect rejection. Browser tests cover login failures/validation, workspace selection, logout, generic reset responses, password confirmation, cleared fragments/storage, expired and platform-only society denial, accessibility in both themes, responsive keyboard navigation and static/private PWA cache boundaries. Browser mocks represent server responses and leave production guards enabled; real cookie/CSRF/tenant/DB tests run in the backend suite.

Deployment manual checks: configure and verify real TLS SMTP delivery, HTTPS reverse-proxy forwarding/secure cookies, and trusted proxy IP; open a real reset mail and verify it cannot be reused. No SMTP credentials were provided during development, so delivery tests use an injected mail adapter.
